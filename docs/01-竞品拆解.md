# 竞品拆解：公众号文章抓取 → 文档导出（GitHub 开源生态）

> 调研时间：2026-10　｜　调研方式：GitHub Search API + 各仓库 README / package.json / requirements.txt / Issue 原文
> 目的：为「捕获公众号文章并导出为保留文字与图片排版的 Word」这一需求，找出可借鉴的架构，同时避开已经失效的技术路线。

---

## 0. 结论速览

1. **整个生态可以分成三派**，而且各有明确的生死状态：

   | 流派 | 代表 | 抓取来源 | 2026-10 现状 |
   |---|---|---|---|
   | **A. 公众号后台 API 派** | wechat-article-exporter（13k★） | 公众号后台「写文章 → 超链接 → 搜索公众号文章」接口 | **已被微信关闭上游接口**，项目 2026-07-30 归档停止维护 |
   | **B. 浏览器登录态 / 页面注入派** | Wechatsync（6.4k★）、各类扩展与本地服务 | 用户自己浏览器里已渲染好的页面 DOM | **仍然可用**，是目前唯一稳定的路子 |
   | **C. MITM 代理抓包派** | HeartFlying、wechat_articles_spider 系 | 中间人代理嗅探移动端/客户端请求 | **大幅退化**，微信 4.x 改私有 Native iLink 通道后基本失效 |

2. **所有成熟项目里，Word 都是"顺带导出的第 N 种格式"**，没有一个是把「Word 排版保真」当第一目标的。它们的主战场是 HTML / Markdown / PDF。
3. **没有任何一个项目利用本机 Word/WPS 的 COM 自动化来做高保真转换**。它们要么用 `python-docx` 做语义化重排（干净但排版简化），要么用 `pdf2docx` 做 PDF 回填（保真但不可编辑）。**这是我们的差异化空间，也正好匹配你的 Windows + Office 环境。**
4. 最值得抄的**架构范式**：`单一 Article 内容模型 → 多格式渲染器`（velyvo 项目），以及 `页面注入捕获 + 平台适配器`（Wechatsync）。最值得抄的**工程细节**：图片本地化、廉洁 HTML 清洗、`manifest.json` 可审计产物、并发池 + 断点续传。

## 1. wechat-article/wechat-article-exporter —— 曾经的王者，已归档

| 项 | 内容 |
|---|---|
| 仓库 | [wechat-article/wechat-article-exporter](https://github.com/wechat-article/wechat-article-exporter) |
| 体量 | **13,072 ★ / 2,278 fork**（同类第一） |
| 语言 / 协议 | TypeScript ｜ MIT |
| 状态 | **2026-07-30 起停止维护、转只读归档**（[Issue #200](https://github.com/wechat-article/wechat-article-exporter/issues/200)） |
| 在线站 | down.mptext.top，域名 2026-10-30 到期 |

### 功能清单
- 搜索公众号、拉取全量历史文章列表；缓存列表减少接口请求
- 导出 **html / json / excel / txt / md / docx** 六种格式（HTML 打包图片与样式，宣称 100% 还原排版）
- 按作者/标题/发布时间/原创标识/所属合集过滤；支持合集（专辑）下载
- 支持图片分享消息、视频分享消息
- 导出评论、评论回复、阅读量、转发量（需额外抓包拿 credentials）
- Docker 私有化部署、Cloudflare / Deno Deploy 部署

### 架构拆解
```
Nuxt 3 (SSR + Vue 3 前端)
├─ pages/ pages2/          登录扫码、公众号列表、文章列表 UI
├─ utils/index.ts (112KB)  核心：接口签名、分页、字段解析、格式转换入口
├─ utils/appmsg.ts         公众号后台 appmsg 列表接口封装
├─ utils/album.ts          合集（专辑）解析
├─ utils/comment.ts        评论/阅读量抓取
├─ utils/download/
│   ├─ BaseDownloader.ts   下载器抽象基类
│   ├─ Downloader.ts       文章 HTML 抓取 + 图片本地化（20KB）
│   ├─ Exporter.ts         多格式导出编排（36KB）
│   └─ ProxyManager.ts     代理池
├─ utils/pool.ts           并发池
└─ 存储：Dexie(IndexedDB)  列表缓存 / 任务状态
```

**技术栈**：Nuxt 3 + Vue 3 + @nuxt/ui + Tailwind + TypeScript；`cheerio` 解析 HTML；`turndown` 转 Markdown；`html2pdf.js` + `puppeteer` 出 PDF；`exceljs` 出 Excel；`jszip` 打包；`DOMPurify` 清洗；`ag-grid` 表格；`p-queue` 调度；`zod` 校验。

**核心原理（已失效的那根地基）**：利用公众号后台「写文章 → 插入超链接 → 搜索其他公众号文章」这个官方功能所调用的接口，来拿任意公众号的文章列表。用户扫码登录自己的公众号，用自己账号的登录态去请求。

### 优点
- 全流程最完整，把「列表 → 详情 → 图片 → 多格式 → 数据统计」全打通；UI 成熟
- 工程化程度高：并发池、代理管理、列表缓存、增量更新
- HTML 导出确实是 100% 还原（因为它把原始内联样式 + 样式表 + 图片整包下载）

### 缺点 / 教训
- **单点依赖致命**：整条链路压在一个非公开接口上，微信一关就全废。作者原话："这不是一个可以靠改代码绕过去的问题"
- 需要用户自己的公众号登录态 → 有账号风险（风控/封号），且必须是有后台权限的号
- 单机浏览器里做重活，大批量导出时内存与 I/O 压力大
- **DOCX 只是附属产物**：依赖清单里没有专门的 docx 库，官方文档反复强调"只有 HTML 能 100% 还原"，等于承认 Word 一定有排版损失

### 可借鉴
`BaseDownloader / Exporter` 的分层、图片本地化、并发池 + 断点续传、`manifest` 式产物清单。**不要借鉴它的抓取入口。**

## 2. rachelos/we-mp-rss —— Python 派的工程化标杆

| 项 | 内容 |
|---|---|
| 仓库 | [rachelos/we-mp-rss](https://github.com/rachelos/we-mp-rss) |
| 体量 | **4,941 ★ / 821 fork** |
| 语言 / 协议 | Python ｜ 自定义（NOASSERTION） |
| 状态 | 活跃（2026-10 仍在提交） |

### 功能清单
- 把公众号变成 **RSS 订阅源**，支持定时更新、标签订阅、Webhook / API / AI Agent 接入
- 公众号文章转 Markdown、转 PDF
- 多用户、鉴权（JWT + bcrypt）、Docker 部署

### 架构拆解
```
FastAPI (uvicorn) ── Vue 前端
├─ APScheduler        定时抓取调度
├─ SQLAlchemy         多库适配：SQLite / MySQL / PostgreSQL
├─ Playwright + playwright-stealth + Selenium   浏览器自动化（登录、翻页、反检测）
├─ BeautifulSoup4 + lxml + markdownify          HTML → Markdown
└─ 导出链：python-docx / docx2pdf / pdf2docx / reportlab / markitdown / PyMuPDF
```

**技术栈亮点**：`playwright-stealth` 做无头浏览器反检测；导出侧同时装了 `pdf2docx`（PDF→Word）、`docx2pdf`（Word→PDF）、`markitdown`（各类→Markdown），说明作者试过多种互转路线。

### 优点
- 后端语言与生态选得对（Python 做 HTML 清洗/文档生成最省事）
- 定时 + RSS 化是很好的产品思路，适合"持续归档"而不是"一次性下载"
- 多数据库适配、鉴权、Docker 完整，可直接私有化

### 缺点
- 依赖浏览器自动化 + 登录态，重、慢、易被风控；stealth 也只是延缓
- 仍然要吃公众号后台/搜索的登录态，**同样受 A 派地基塌陷的影响**
- 依赖臃肿（docx2pdf / pdf2docx / markitdown 全装），环境体积大
- 输出优先 MD/PDF，Word 属于附带

### 可借鉴
1. **`pdf2docx` 这条路值得记下来**：先渲染 PDF 再转 Word，是"排版保真优先"的一种解法（代价是 Word 里元素变成文本框，编辑性差）。
2. Python 后端 + 独立前端的进程结构，适合做成常驻本地服务。
3. `playwright-stealth` 的浏览器兜底思路（我们只在必要时用）。

| 语言 / 协议 | Python ｜ CC BY-NC-SA 4.0（**禁止商用**，二开需署名） |

### 功能清单
- 9 平台：微信公众号（**单篇 / 多篇批量 / 公开专辑合集 `appmsgalbum`**）、知乎、微博、简书、新浪博客、CSDN、掘金、博客园、51CTO
- 导出：Markdown / HTML / PDF / **Word** / TXT / 纯链接 / ZIP 全能包
- **双模态输出**：整卷合并大文件 + 独立分篇
- **3 档配图**：压缩图（省 70%+）/ 高清原图 / 纯文本无图
- 离线 HTML 单文件（内置侧边栏目录树、全文搜索、明暗主题）
- `manifest` / 断点保护 / 分批打包

### 架构拆解
```
Windows 桌面客户端（外壳）
└─ 本地渲染引擎 127.0.0.1:8000  (FastAPI + uvicorn)
   ├─ 平台适配器：wechat / zhihu / weibo / jianshu / csdn / juejin ...
   ├─ 抓取：Playwright Chromium（含 headless PDF 渲染内核）
   ├─ 提纯与排版引擎：去噪、配图三档、链接提取、目录大纲
   └─ 导出：MD / HTML / PDF(Chromium) / DOCX / TXT / ZIP
```

### 优点
- **架构判断最准**：明确写"云端 OOM + 机房 IP 被 WAF 封"是原罪，于是全面转 **Local-First**——100% 本地运算、用本地宽带上网。这正是我们该走的形态。
- 公众号抓取范围写得最诚实：**只支持「公开专辑/合集链接 + 单篇/多篇公开链接」**，并明说"旧版通过本地代理嗅探全号历史文章的方案暂时停用（微信 4.x 改私有 Native iLink 通道）"。
- 用 Chromium 出 PDF（保真）而不是硬啃 Word，产品取舍清晰；Word 用"原生 Heading 层级 + 图片居中内嵌 + 表格规整"的语义化路线。
- 配图三档 / 双模态输出的产品设计非常值得抄。

### 缺点
- 体量小、验证不足（40★），Star 数不代表质量但样本少
- 协议 **CC BY-NC-SA 4.0 + 强制署名**，参考可以，**不能复制代码进我们的项目**
- 依赖 Playwright Chromium 安装包（几百 MB），首启成本高
- Word 仍是"语义化重排"，不是保真渲染

### 可借鉴
Local-First 形态、`127.0.0.1` 本地引擎 + 浏览器工作台、合集链接解析、配图三档、双模态（合卷 + 分篇）输出、`manifest` 断点保护。

## 4. velyvo/export-wechat-articles —— 代码质量最高的「单一模型多渲染」范本

| 项 | 内容 |
|---|---|
| 仓库 | [velyvo/export-wechat-articles](https://github.com/velyvo/export-wechat-articles) |
| 体量 | 0 ★（几乎无人知晓，但工程质量最高） |
| 语言 / 协议 | Python 3.10+ ｜ 未声明 |
| 形态 | 便携 CLI + Agent Skill |

### 功能清单
- 一次获取，输出 **Markdown / HTML / DOCX / PDF** 四格式
- 图片本地化到 `assets/`；表格语义化转换；行内颜色映射到 DOCX
- 小程序卡片、公众号名片 → 转为带封面/头像的静态参考卡片
- `--input-html` **兜底**：自动抓取被验证页拦截时，用浏览器"另存为"的 HTML 继续处理
- 每篇产出 `manifest.json`（源 URL、元数据、版本、文件哈希、资源清单、告警）
- 安全：URL 白名单（只收 `mp.weixin.qq.com/s...`）、DOMPurify 式清洗（去脚本/表单/事件）、图片域名白名单（微信/腾讯 CDN）、不执行文章内 JS
- 重复执行检查 `manifest.json` → `skipped:true`，可断点恢复

### 架构拆解（这份流程图值得直接抄）
```
公开公众号 URL
   → 获取并验证页面（HTTP，失败则 Chromium 回退）
   → 提取 #js_content 正文节点
   → 清洗危险节点（script/form/on* / 危险协议）
   → 下载并本地化图片（微信 CDN 白名单 + 大小上限）
   → 统一 Article 内容模型   ★ 关键
   → MD / HTML / DOCX / PDF 四个渲染器各自消费同一模型
   → manifest.json（哈希 + 资源 + warnings）
```

**技术栈**：Python 3.10+、`lxml` + `cssselect`（解析与选择器）、`Pillow`（图片处理）、`python-docx`（Word）、Chromium（PDF）、`uv` 管理依赖、`unittest` 测试。

### 优点
- **架构最干净**：一份内容模型喂多个渲染器，彻底避免"各格式之间文字/图片/版本对不上"
- 工程规范最好：哈希、清单、告警、断点恢复、安全白名单、有测试
- 明确承认边界："DOCX 是可编辑的语义化转换，不是浏览器截图"——**诚实的产品声明**
- `--input-html` 兜底设计极其实用

### 缺点
- 无 UI，纯 CLI；对普通用户不友好
- DOCX 靠 `python-docx` 手工映射，样式覆盖有限（`section` 卡片、背景色块、圆角、绝对定位都会丢）
- 单人项目、无社区，长期维护无保障

### 可借鉴
**这是我们的主骨架**：`Article 内容模型 + 多渲染器 + manifest` 三段式，加上 `--input-html` 兜底与安全白名单。

## 5. wechatsync/Wechatsync —— 「页面注入捕获」流派的最佳范例

| 项 | 内容 |
|---|---|
| 仓库 | [wechatsync/Wechatsync](https://github.com/wechatsync/Wechatsync) |
| 体量 | **6,461 ★ / 1,080 fork** |
| 语言 / 协议 | TypeScript ｜ **GPL-3.0（强传染，不能抄代码）** |
| 状态 | 活跃（2026-10-17 仍在提交，默认分支 v2） |

### 定位
一键把文章同步到今日头条、WordPress、知乎、简书、掘金、CSDN、Typecho 等多个平台。**它不是下载器，但它的"捕获"部分正是我们要的。**

### 架构拆解
```
Chrome 扩展 (MV3)
├─ content_script   注入目标页面，读取已渲染的 DOM（含图片、样式）
├─ background       消息路由、跨域请求中转、登录态复用
├─ 中间规范化层     抓到的 HTML → 平台无关的统一文章结构
└─ adapters/        每个目标平台一个适配器（各自的编辑器 DOM 操作）
```

### 优点
- **抓的是浏览器里已经渲染好的 DOM**：懒加载图片已就位、`data-src` 已被 JS 换到 `src`、动态注入的卡片已生成 —— 这一步绕过了绝大多数反爬
- **不需要任何登录 cookie 或 token 索取**，用的是用户当前这个页面
- 6.4k★ / 1k fork 长期活跃，说明"页面注入 + 适配器"这条架构是真的能活很多年
- 适配器模式：加平台只加一个 adapter，核心不动

### 缺点
- 是"发送"工具不是"归档"工具，导出物是推到别的平台而不是本地文件
- **GPL-3.0**：代码有传染性，我们不能复制，只能学架构
- 扩展形态受 MV3 限制（Service Worker 生命周期、跨域权限收紧）
- 扩展安装有门槛（开发者模式加载）

### 可借鉴
**"捕获已渲染 DOM"是最高保真的取内容方式**；适配器分层；用扩展做「入口」、用本地服务做「重活」的混合形态。

## 9. 对我们的五条关键启示

1. **别碰后台 API 与 MITM**：地基已经塌了，任何"全号历史抓取"的承诺都是在给自己埋雷。老老实实做「单篇 + 合集 + 页面注入」。
2. **抄 velyvo 的三段式骨架**：`Article 内容模型 → 多渲染器 → manifest`。这是唯一能保证"Word 里出现的图和字，跟 HTML/PDF 里完全一致"的结构。
3. **抄 Wechatsync 的捕获思路**：最高保真的内容不是 HTTP 抓来的字符串，而是浏览器里**已经被 JS 跑完**的 DOM。给用户一个"在页面上一键捕获"的入口，能省掉 80% 的反爬对抗。
4. **形成我们自己的护城河**：三个渲染器里，**Word 用本机 Word COM 做高保真**，这是所有开源项目都没做的事，而你的机器上 Word + WPS + Chrome 全都有。
5. **守住合规与边界**：只处理公开可访问的文章、不绕过验证码/付费墙/删文限制、产物仅供个人存档、自带 `manifest` 便于追溯来源与授权状态。
