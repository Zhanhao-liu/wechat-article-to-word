## 二、Word COM 为什么被否决（实测证据）

调用链是通的：

```
DispatchEx("Word.Application")  →  Word 16.0 启动成功（独立进程）
app.Visible = False / DisplayAlerts = 0 / AutomationSecurity = 3  →  全部设置成功
app.Documents.Open("probe.html")  →  ✗ 崩
```

**崩溃表现**（不是参数错误，是进程死了）：

| 尝试 | 结果 |
|---|---|
| `Open(只给文件名)` | 14.2 秒后 `com_error -2147023170 远程过程调用失败` |
| `Open(+ConfirmConversions/ReadOnly/AddToRecentFiles)` | 0ms `-2147023174 RPC 服务器不可用` |
| `Open(+Visible=False)` | 同上 |
| `Open + SaveAs2(docx)` | 同上 |
| `Documents.Add + Content.InsertFile(html)` | 同上 |

第一条失败后 Word 进程就已消失，后续全部报「RPC 服务器不可用」＝ **Word 在导入 HTML 时崩溃退出**。

**这是环境问题，不是代码问题**：Office 的 HTML 导入转换器在这台机器上导入即崩。这类问题无法通过换参数绕过，也不值得为用户环境去修。

### 即便修好，也不该用 COM —— 三个理由

1. **收益窄**：COM 相对 python-docx 的优势只在「背景图卡片 / 圆角 / 多列浮动」。而这几类节点转成图片插入，效果等同且更稳。
2. **代价高**：依赖 Word 进程、不能并发、可能弹窗、可能卡死、可能崩溃，还要处理进程泄漏。
3. **不可移植**：换台没装 Office 的机器就废，而 `python-docx` 只需要 pip。

> **决策：主渲染器只用 `python-docx`，彻底移除 COM 与 `pywin32` 依赖。**

## 三、python-docx 到底能还原多少（已逐项验证）

`scripts/demo_docx.py` 生成了一份刻意模仿公众号排版的样例 `tmp/probe/demo_article.docx`，已逐项验证：

| 公众号常见排版元素 | python-docx 支持 | 实现方式 |
|---|---|---|
| 标题：居中、加粗、18pt | ✅ | `paragraph.alignment` + `run.font` |
| 作者行：灰度小字居中 | ✅ | `RGBColor` + 字号 |
| 正文：字色 `#3F3F3F`、1.75 行距、段后 8pt | ✅ | `paragraph_format` |
| 行内加粗变色、下划线、行内代码（等宽字体） | ✅ | 逐 `run` 设置 |
| 中文字体（不跳宋体） | ✅ | `w:rFonts` 的 `ascii`/`hAnsi`/`eastAsia` 三者齐写 |
| 居中图片 + 图注 | ✅ | `add_picture(width=...)`，图片**写进 docx** |
| 引用块：浅灰底 + 左侧竖条 + 缩进 | ✅ | `w:shd` 段落底纹 + `w:pBdr` 段落边框 |
| 小标题左侧彩色竖条 | ✅ | 同上 `w:pBdr` |
| 表格：表头深底白字 + 斑马纹 | ✅ | 单元格 `w:shd` + `Table Grid` |
| 项目符号 / 自动编号列表 | ✅ | `List Bullet` / `List Number` 样式 |
| 可点击超链接 | ✅ | 手写 `w:hyperlink` + `relate_to` |
| 页脚页码「第 X 页 / 共 Y 页」 | ✅ | `w:fldChar` 域代码 |
| A4 + 中文常用页边距 | ✅ | `section.page_*` |
| 背景图卡片、圆角、多列浮动 | ⚠️ 部分 | **转成图片插入**（Chrome 无头截图，M2 再做） |
| 内联 SVG 图标 | ❌ | 渲染时删除（原文多为装饰） |
| 视频/音频/小程序卡片 | ❌ | 降级为「说明文字 + 原文链接」 |

**结论：95% 的公众号排版元素 python-docx 都能精确还原，剩下 5% 用「转图」兜底。**

## 四、顺带探明的环境约束（写进实现注意事项）

| 约束 | 现象 | 对策 |
|---|---|---|
| `%TEMP%` 不可写 | pywin32 写 `gen_py` 报 `WinError 5` | 已不需要 pywin32；若将来要用，先把 `TEMP` 指向工作区 |
| `D:\` 与 `D:\lzh_own\` 不可写 | 建目录报 `WinError 5`（卷 ACL 限制） | 产物一律落在工作区内，可配置输出目录 |
| 中文路径 | 正常工作 | 无需 8.3 短路径 |
| 无 Node / git / pandoc | — | 方案已避开（纯 Python 栈） |
| 代理 | 系统代理 `127.0.0.1:7890`，但抓微信必须直连 | 请求侧强制 `trust_env=False` 并清空 `*_PROXY` |

## 五、修正后的方案要点（替代 03 文档第 7 节）

```
单一渲染链：
  blocks[] ──► docx_renderer (python-docx)
                 ├─ 页面/页边距/页脚页码
                 ├─ 标题 → 居中加粗大字号
                 ├─ 段落 → run 级字色/字重/字号 + 行距/缩进/对齐
                 ├─ 引用 → 段落底纹 + 左边框
                 ├─ 图片 → add_picture（内嵌，按版心宽等比缩放）
                 ├─ 表格 → Table Grid + 表头底纹 + 斑马纹
                 ├─ 列表 → List Bullet / List Number
                 └─ 卡片 → 截图转图片（M2）
              ──► article.docx  ──► manifest.json
```

- **不再有 `--mode fidelity/clean/exact` 三档**。Word 输出只有一种：`python-docx` 渲染。
- 保留「HTML 离线单文件」作为**保真参照物**（用来比对 Word 有没有丢内容），也是给用户的另一种存档格式。
- 如果将来确实需要「像素级一致」，用 Chrome 无头出 PDF（`--pdf`），**不经 Word**。
