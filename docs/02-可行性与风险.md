# 可行性与风险：这篇文档决定「我们能承诺什么、不能承诺什么」

> 结论先行：**能稳定做的是「单篇文章 → 保排版 Word」；不能承诺的是「一键下载某公众号全部历史文章」。** 后者在 2026 年已被微信从上游关掉，任何声称能做的开源项目都已停更或半残。

---

## 1. 微信侧现状时间线（这是所有技术选型的前提）

| 时间 | 事件 | 影响 |
|---|---|---|
| ≤2024 | 公众号后台「写文章 → 超链接 → 搜索其他公众号文章」接口可用 | A 派（后台 API）黄金期，13k★ 项目靠它 |
| 2024–2025 | 单篇页面改版：`#activity-name`/`#js_name`/`#publish_time` 等 id 逐步并入 `window.cgiDataNew` | 老代码按 id 取标题会拿到空值 |
| 2026-07-30 | 上游核心接口被微信关闭 | [wechat-article-exporter 归档停维](https://github.com/wechat-article/wechat-article-exporter/issues/200)，作者："开箱即用的一键同步公众号文章已不复存在" |
| 2026-09 | `profile_ext?__biz=...&action=home&f=json` 返回 `msg_count:0, home_page_list:[]`，需微信内环境 | MITM/C 派不可规模化，[讨论](https://github.com/wechat-article/wechat-article-exporter/issues/199) |
| 2026-10 | 微信 4.x 改用私有 Native iLink 通道 | 本地代理嗅探全号历史方案停用（BlogDistiller 官方说明） |

**推论**：任何「输入公众号名 → 拉全部文章」的产品承诺，今天都是空头支票。我们的产品边界必须在这条线上画清楚。

## 2. 三条抓取通道的实况与取舍

| 通道 | 做法 | 稳定性 | 保真度 | 用户成本 | 我们是否用 |
|---|---|---|---|---|---|
| **T1 URL 抓取** | 用户粘贴 `mp.weixin.qq.com/s/...`，服务端 HTTP GET + Chromium 兜底 | 中（可能遇验证页/风控页） | 高（拿到原始 DOM） | 极低（复制链接） | ✅ **主通道** |
| **T2 页面注入捕获** | 浏览器扩展 / 书签小工具，读用户浏览器里**已渲染完**的 DOM，POST 给本地服务 | 高（绕过绝大多数反爬） | **最高**（懒加载图已就位、动态卡片已生成） | 中（装扩展/拖书签） | ✅ **保真主通道** |
| **T3 粘贴/另存 HTML** | 用户 Ctrl+S 存网页，或全选复制，把 HTML 交给工具 | **最高**（永远可用） | 高 | 低（一次操作） | ✅ **兜底通道（必做）** |
| T4 公众号后台 API | 扫码登录自己公众号，调 `appmsgpublish` | 低（`200013 freq control`、`ret:-6` 账号级封禁隔天恢复） | 高 | 高（需有后台权限的号，有封号风险） | ❌ 不做 |
| T5 MITM 代理 | 装证书 + 抓包拿 token/fakeid | 极低（4.x 私有通道已废） | 中 | 极高 | ❌ 不做 |
| T6 搜狗微信搜索 | `weixin.sogou.com/weixin?type=2&query=` | 中（仅前 10 页、有验证码、跳转为重定向链） | 中 | 低 | 🔶 可选（做"找文章"入口，不做全量） |
| T7 第三方 RSS | 微信读书体系取正文（we-mp-rss 路线） | 中 | 中 | 中（要读书账号） | ❌ 不做 |

**最终选择：T1 + T2 + T3 三通道并存，互为兜底。** 这三条的共同点是——**都不需要用户交出任何账号，都不触碰被封的接口**。

## 3. 单篇文章解析的 7 个真实坑（决定成败的细节）

这些是社区与头部项目 Issue 里反复出现的问题，直接写进我们的清洗规则：

1. **正文默认是隐藏的。** `#js_content` 带内联 `style="visibility:hidden"`，靠 JS 改可见。直接抓 HTML 后必须先移除该 style，否则拿到的"是空内容"。→ 规则：`removeAttr('style')` 后再判定是否为空。
2. **元数据已迁移。** 新版页面标题/号名/时间在 `window.cgiDataNew` 的脚本变量里，不是 DOM id。→ 规则：**DOM 取不到时回退解析内联 JS 变量**（`cgiDataNew` / `nickname` / `ct`）。
3. **图片真地址在 `data-src`。** `src` 只是占位 gif。→ 规则：`src = data-src || src`，并**删掉 `height` 属性**（否则图片被压扁）。
4. **必须删除的噪声节点**（否则导出里全是垃圾）：`#js_top_ad_area`、`#content_bottom_area`、`#js_pc_qr_code`、`#js_tags_preview_toast`、全部 `<script>`；文末"阅读/赞/分享"是 `data:image/svg+xml` 内联图标，也会污染导出。
5. **图片防盗链。** `mmbiz.qpic.cn` 在第三方域名直接当 `<img src>` 引用会拿占位图/403。→ 规则：**一律下载到本地再嵌入**。至于 Referer 该带 `https://mp.weixin.qq.com/` 还是空，社区说法不一致、随时段域名波动，→ 实现上做成**可切换的 Referer 策略 + 失败自动重试**。
6. **格式兼容。** `webp` Word 2016/旧 WPS 不支持，`gif` 在 Word 里只剩首帧。→ 规则：入库统一转 `png/jpeg`，可选保留原 gif 另存。
7. **风控页识别。** 返回内容里若出现"环境异常/请在微信客户端打开/该内容已被发布者删除"，不能当成正文解析，要给出**明确可执行的提示**（引导用 T2/T3 通道）。

## 4. Word 保真的六条路线实测对比（核心决策）

| 路线 | 原理 | 保真度 | 可编辑性 | 本机可行性 | 结论 |
|---|---|---|---|---|---|
| **W1 python-docx 语义化** | 自己遍历 DOM，映射成段落/标题/图片/表格/颜色 | ★★☆ | ★★★★★ | ✅ uv 装 | 干净、稳，但 `section` 卡片/背景/圆角/浮动图必丢 |
| **W2 pandoc** | HTML → docx | ★☆ | ★★★★ | ❌ 未装 pandoc | **丢弃内联 style**（连 `text-align` 都不留），公众号全内联样式基本还原不出来，[pandoc#10872](https://github.com/jgm/pandoc/issues/10872)。**淘汰** |
| **W3 html-to-docx (npm)** | 解析 HTML 生成真 OOXML | ★★★ | ★★★★ | ❌ 本机无 Node | 只吃 base64 图片，外链 `<img>` 直接丢，[#59](https://github.com/privateOmega/html-to-docx/issues/59)；图片套在某些标签内不渲染。**淘汰** |
| **W4 LibreOffice headless** | `soffice --convert-to docx` | ★★ | ★★★ | ❌ 未装 | HTML 支持弱，圆角/背景/嵌套 section 全丢。**淘汰** |
| **W5 Word COM 自动化** | 本地化 HTML 存盘 → `Documents.Open` → `SaveAs2(wdFormatXMLDocument)` | **★★★★★** | ★★★★★ | ✅ **Word 16.0.14334 + COM 已注册** | **保真最高**：真 Word 排版引擎，圆角背景/浮动图/表格都能留；且完全可编辑。代价：依赖 Word、不能高并发、需防弹窗卡死 |
| **W6 PDF 中转** | Chromium `--print-to-pdf` → `pdf2docx` 回填 | ★★★★☆ | ★☆ | ✅ **Chrome 155 已装**（无头） | 版面锁死，Word 里元素变文本框/图片，几乎不可编辑；且 Chromium 分页裁切是已知 bug（常要做单页长 PDF） |

### 决策（已按实测修正）：**只用 W1 `python-docx`，放弃 W5 Word COM**

```
Word 输出只有一种渲染链：
  blocks[] ──► docx_renderer (python-docx) ──► article.docx
保真参照物另出：article.html（离线单文件）
需要像素级一致时：Chrome 无头 --print-to-pdf ──► article.pdf（不经 Word）
```

**为什么放弃 W5（原定的"保真主线"）—— 有实测证据，不是主观取舍：**

M0 探针在本机实测，Word COM 链路在最后一步崩了：`DispatchEx` 成功启动 Word 16.0，参数也设置成功，但 `Documents.Open("probe.html")` 让 **Word 进程直接崩溃退出**（首条报「远程过程调用失败」，随后全部报「RPC 服务器不可用」）；`Open` 的 4 种参数组合与 `Add + InsertFile` 共 5 条路径全部失败。这是本机 Office 的 HTML 导入转换器问题，换参数绕不过去。

即便修好也不该用，理由三条：
- **收益窄**：COM 相对 python-docx 的优势只在「背景图卡片 / 圆角 / 多列浮动」，而这几类节点转成图片插入效果等同且更稳；
- **代价高**：依赖 Word 进程、不能并发、可能弹窗/卡死/崩溃，还要处理进程泄漏；
- **不可移植**：换台没装 Office 的机器就废，而 python-docx 只需 `pip install`。

W1 的实际还原能力已逐项验证（见 [05-探针结论](./05-探针结论.md)）：标题/字色/字重/行距/缩进/居中图/图注/引用块底纹与左边框/表格底纹与斑马纹/项目符号/超链接/页脚页码/中文字体，**95% 的公众号排版元素都能精确落进 Word**；剩下 5%（背景图卡片、圆角、多列）用「转图」兜底。

## 6. 风险清单与缓解

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| R1 | 单篇 URL 抓到验证页/风控页 | 中 | 抓取失败 | 三通道兜底：HTTP → 无头 Chrome → 用户粘贴 HTML；错误给出可执行指引而非堆栈 |
| R2 | 图片防盗链导致图裂 | 高 | 产物不可用 | 强制本地化 + Referer 策略可切换 + 失败重试 + 转码；`manifest` 记录失败图与原因 |
| R3 | ~~Word COM 弹窗/卡死/进程泄漏~~ → COM 已弃用 | — | — | 不再引入 Word 进程依赖，该项风险消失 |
| R4 | Word 保真仍是"尽力而为" | 高 | 预期偏差 | **产品文案明确：Word 是语义化重排，不是截图**；背景卡片等复杂块转图；需要像素级一致时引导用 `--pdf` |
| R5 | 版权与合规 | 中 | 法律风险 | 仅处理公开文章；不绕过登录/验证码/付费墙/删文；产物仅供个人存档；`manifest` 记录来源与"仅个人使用"声明；不内置任何批量分发能力 |
| R6 | 微信改版导致解析失效 | 高 | 功能退化 | 解析规则集中在 `extract/` 一层、写清每个选择器的用途；建立 `samples/` 真实 HTML 回归测试集，改版时只改一处 |
| R7 | 复杂排版块（背景图卡片/圆角/多列）无法用文字还原 | 中 | 观感偏差 | 这类节点用 Chrome 无头截图转成图片插入（M2 实现），并用 `text_fallback` 保证信息不丢 |
| R8 | 依赖体积（Playwright Chromium 数百 MB） | 中 | 首启慢 | **不默认装 Playwright**，优先复用本机 Chrome 155（`--headless=new`），仅 T2 扩展场景才考虑 |

## 7. 能力边界（写进 README 的"能/不能"）

**能做**
- ✅ 单篇文章 URL → 保留文字 + 图片 + 主要排版的 Word/PDF/HTML/MD
- ✅ 多篇 URL 批量（逐篇串行/小并发，带断点续传）
- ✅ 公开专辑/合集页（`appmsgalbum`）解析出文章清单后批量导出
- ✅ 浏览器页面一键捕获（最高保真通道）
- ✅ 每篇产出 `manifest.json`（来源、哈希、图片清单、告警）

**不做 / 不能承诺**
- ❌ 输入公众号名 → 下载全部历史文章（上游接口已关闭）
- ❌ 绕过登录、验证码、付费墙、已删除内容
- ❌ 抓取阅读量/点赞/评论数（需额外抓包，风险高）
- ❌ 保证 Word 与网页像素级一致（这是 PDF/长图的职责）
- ❌ 任何形式的批量再分发/公开发布
