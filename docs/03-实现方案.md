## 1. 目标与非目标

### 目标（按优先级）
1. **一篇公众号文章 → 一个 Word 文件，文字完整、图片全在文件里、主要排版保留**（标题层级、段落、颜色、居中、引用、表格、卡片）
2. 图片**必须内嵌进 docx**（不是外链），断网打开也不能有红叉
3. 操作门槛低：粘贴一个链接就能出结果；出问题时能自动换路子
4. 产物**可审计**：每篇带 `manifest.json`（来源、哈希、图片清单、告警）
5. 全程**只在本机跑**，不上传任何内容，不需要任何账号

### 非目标（明确不做，避免过度设计）
- ❌ 输入公众号名 → 下载全部历史文章（上游接口已被微信关闭，见 02 文档）
- ❌ 抓阅读量/点赞/评论（需抓包，风险高、收益低）
- ❌ 绕过登录、验证码、付费墙、已删除内容
- ❌ 云端服务 / 账号体系 / 多人协作
- ❌ 保证 Word 与网页像素级一致（那是 PDF/长图模式的职责）

## 3. 总体架构（六层，单向下行）

```
┌───────────────────────── 接入层 input ─────────────────────────┐
│  URL 单篇 │ URL 列表/文件 │ 粘贴或另存 HTML │ 书签工具 POST │ 合集页 │
└───────────────────────────────┬───────────────────────────────┘
                                ▼
┌───────────────────────── 抓取层 fetch ─────────────────────────┐
│  HttpFetcher(httpx)  →  ChromeFetcher(--headless=new)  →  手动HTML │
│  ▲ 风控/验证页识别 guard：命中即降级到下一通道                        │
└───────────────────────────────┬───────────────────────────────┘
                                ▼  原始 HTML
┌───────────────────────── 解析层 extract ───────────────────────┐
│  meta：标题/号名/作者/时间/原创（DOM 取不到 → 回退 window.cgiDataNew）│
│  content：#js_content 正文树；噪声节点剔除                          │
└───────────────────────────────┬───────────────────────────────┘
                                ▼  Raw DOM 子树
┌─────────────────────── 归一化层 normalize ──────────────────────┐
│  10 步清洗管道 → **Article 内容模型（blocks[]）**  ★核心资产        │
│  section 压平 │ 懒加载图归一 │ 内联样式→结构化 │ 卡片转图 │ 表格/列表 │
└───────────────────────────────┬───────────────────────────────┘
                                ▼
┌───────────────────────── 资源层 assets ────────────────────────┐
│  图片下载（Referer 策略可切换/重试/白名单）→ 转码 png/jpeg        │
│  → assets/img_001.png + sha1 + 尺寸                              │
└───────────────────────────────┬───────────────────────────────┘
                                ▼
┌───────────────────────── 渲染层 render ────────────────────────┐
│  docx_renderer（python-docx） │ pdf │ html │ md │
└───────────────────────────────┬───────────────────────────────┘
                                ▼
┌───────────────────────── 产物层 output ────────────────────────┐
│  <标题>_<日期>_<短哈希>/ article.docx │ article.pdf │ assets/ │ manifest.json │
└───────────────────────────────────────────────────────────────┘
```

**架构的两个关键决定**
1. **`blocks[]` 是唯一的中间表示**（抄 velyvo 的做法）：任何渲染器都不再碰 HTML。这样"Word 里的图 = HTML 里的图 = PDF 里的图"是结构上保证的，而不是靠三套代码各自努力。
2. **抓取通道可降级、渲染档位可降级**：抓不到 → 换通道 → 还不行 → 让用户给 HTML；Word 起不来 → 自动切 `docx_clean`。**任何单点失败都不能让用户拿不到文件。**

## 5. 核心数据模型（`Article`）

这是整个项目最重要的一处设计，先定死它，后面写代码就是填空。

```jsonc
{
  "schema": "w2d.article/1",
  "source": {
    "url": "https://mp.weixin.qq.com/s/xxxx",
    "channel": "http | chrome | dom | html",   // 怎么拿到的
    "fetched_at": "2026-10-20T12:00:00+08:00",
    "html_sha256": "…"
  },
  "meta": {
    "title": "文章标题",
    "account": "公众号名称",
    "author": "作者",
    "publish_time": "2026-10-18 09:30",
    "digest": "摘要",
    "is_original": true,
    "album": "合集名或 null"
  },
  "blocks": [
    { "type": "heading", "level": 2, "runs": [{ "text": "小标题", "bold": true, "color": "#1a1a1a" }] },
    { "type": "paragraph", "align": "left", "runs": [
        { "text": "正文……", "size_pt": 9.5, "color": "#3f3f3f", "bold": false, "italic": false, "link": null }
    ]},
    { "type": "image", "asset": "img_003.png", "width_px": 640, "align": "center", "caption": null },
    { "type": "table", "header": true, "rows": [[[{ "text": "列1" }], [{ "text": "列2" }]]] },
    { "type": "quote",  "runs": [{ "text": "引用内容" }], "bg_color": "#f7f7f7" },
    { "type": "list",   "ordered": false, "items": [[{ "text": "条目一" }]] },
    { "type": "card",   "asset": "card_001.png", "kind": "mp_card|mini_program|account_card",
      "text_fallback": "【小程序卡片】某小程序", "link": "https://…" },
    { "type": "media",  "kind": "video|audio", "text_fallback": "【视频】标题（请在原文查看）", "link": "…" }
  ],
  "assets": [
    { "id": "img_003", "src_url": "https://mmbiz.qpic.cn/…", "file": "assets/img_003.png",
      "sha1": "…", "bytes": 82311, "mime": "image/png", "status": "ok", "reason": null }
  ],
  "warnings": ["图片 2 张下载失败，已用占位符代替"]
}
```

**设计要点**
- `blocks` 只允许上面这 7 种类型 → 渲染器实现简单、行为可预测
- 所有样式都**结构化**（`color`/`size_pt`/`bold`/`align`），不存 CSS 字符串 → 三个渲染器各自自由映射
- `card`/`media` 有 `text_fallback` → 即使转图失败，也不会丢信息
- `assets[].status` 里记失败原因 → `manifest` 能回答"为什么图看不了"

## 6. 归一化管道（10 步，顺序不能乱）

| # | 步骤 | 规则 | 为什么 |
|---|---|---|---|
| 1 | 去噪声 | 删 `#js_top_ad_area`、`#content_bottom_area`、`#js_pc_qr_code`、`#js_tags_preview_toast`、`<script>`、`<style>` 标签 | 否则广告/二维码/阅读数进入正文（[#138](https://github.com/wechat-article/wechat-article-exporter/issues/138)） |
| 2 | 解隐藏 | `#js_content` `removeAttr('style')`，再判空 | 正文默认 `visibility:hidden`，不去掉会"抓到空" |
| 3 | 懒加载图归一 | `src ← data-src \|\| src`；删 `height`；补 `max-width:100%` | 否则拿到占位 gif、图片被压扁 |
| 4 | 内联图标清理 | 删 `src^="data:image/svg+xml"` 的 `<img>`（文末"赞/在看/分享"） | 避免导出末尾一排乱码图标 |
| 5 | 内联样式结构化 | 解析 `style=""` → `{color,size_pt,bold,align,bg_color}` | 后续三个渲染器共用 |
| 6 | **section 压平** | 递归展开 `<section>`：有文本→段落；纯承载 padding/背景→丢弃；带 `background-image`→标记为卡片 | 公众号编辑器产出 5–10 层 section，不压平 Word 里会变成一堆空行 |
| 7 | 卡片转图 | `mp-common-*`、`card`、`background-image` 节点 → 用 Chrome 无头截图为 png，生成 `card` block | 这类视觉块在 Word 里必须丢 CSS，转图最接近原样 |
| 8 | 表格/列表结构化 | `<table>` → `table` block（保留表头）；`<ul>/<ol>` → `list` block | Word 原生支持，语义化优于截图 |
| 9 | 媒体降级 | 音视频/小程序 → `media` block，带 `text_fallback` + 原链接 | 不下载媒体流（体积/合规），但信息不丢 |
| 10 | 收尾 | 合并连续空段落、去尾部空块、`&amp;` 反转义、URL 规范化 | 产物干净 |

规则 6 的核心伪代码（这是同类项目里最容易写错的地方）：

```python
def flatten(node, ctx):
    """递归压平 section；返回 Block 列表"""
    if is_noise(node): return []
    if has_background_image(node) and has_no_visual_content(node):
        ctx.cards.append(node)           # 交给第 7 步截图
        return [Block.card(pending=node)]
    if node.tag == "img":
        return [Block.image(src=node["data-src"] or node["src"], width=node.get("width"))]
    if node.tag == "table":  return [Block.table(node)]
    if node.tag in ("ul", "ol"): return [Block.list(node)]
    if is_block_container(node):          # section / div 只是一层壳
        return [b for child in node.children for b in flatten(child, ctx)]
    if has_visible_text(node):
        return [Block.paragraph_from(node)]    # 叶子文本节点成段
    return []
```

## 7. Word 渲染（单一渲染链，基于 python-docx）

> ⚠️ **已按实测修正**：原先设计的「三档渲染（含 Word COM 保真档）」已被否决——本机 Word 打开 HTML 会直接崩溃，且 COM 只对边缘场景有优势，不值得引入。详见 [05-探针结论](./05-探针结论.md)。现在 Word 输出只有**一条**渲染链。

```
blocks[] ──► docx_renderer (python-docx) ──► article.docx ──► manifest.json
```

渲染顺序：页面与页边距 → 页脚页码 → 标题（居中/加粗/大字号）→ 正文（run 级字色、字重、字号 + 行距、首行缩进、对齐）→ 小标题（左侧竖色条）→ 图片（**内嵌**，按版心宽等比缩放）→ 图注 → 引用块（段落底纹 + 左边框）→ 表格（`Table Grid` + 表头底纹 + 斑马纹）→ 列表（`List Bullet` / `List Number`）→ 卡片（截图转图）→ 结尾信息块（来源/原文链接）。

### 7.2 保真参照物与「像素级」出口

| 需求 | 做法 | 说明 |
|---|---|---|
| 想知道 Word 有没有丢内容 | 同时产出 `article.html`（离线单文件，图片内联 base64） | 用浏览器并排比对，是最可靠的验收手段 |
| 要像素级一致（打印/留证） | `--pdf` → Chrome `--headless=new --print-to-pdf` | **不经 Word**，避免分页裁切问题；可出单页长 PDF |
| 要干净可二次排版 | 就是默认的 docx | 标题用真实段落样式，可生成导航窗格与目录 |

## 8. 图片处理（决定"有没有红叉"）

```
img.src ─► 域名白名单校验（mmbiz.qpic.cn / mmbiz.qlogo.cn / res.wx.qq.com）
        ─► 下载：Referer 策略 A（空）→ 失败 → 策略 B（https://mp.weixin.qq.com/）
        ─► 校验：Content-Type 是 image 且字节数 > 512B（否则是占位图/错误页）
        ─► 转码：webp → png；gif → 保留原文件 + png 首帧（Word 用 png）
        ─► 压缩档（可选）：长边 > 1600px 或 > 1.5MB 时等比缩放 + JPEG q=85
        ─► 落盘 assets/img_NNN.<ext>，写 sha1/size/mime 进 assets[]
        ─► 全部失败 → 该 image block 降级为「【图片缺失：原因】+ 原链接」
```

**铁律：docx 里只允许嵌入本地文件，绝不允许外链图片。** 这是导出后红叉的第一大原因（综上：外链失效 / 防盗链 / webp 不支持 / 占位 gif）。

## 9. 幂等、命名与产物结构

```
output/
└─ 深度长文：如何读懂财报_20261018_a3f9c1/
   ├─ article.docx
   ├─ article.clean.docx      (可选，另一档)
   ├─ article.pdf             (可选)
   ├─ article.html            (离线单文件，图片内联 base64)
   ├─ article.json            (Article 模型，便于二次加工)
   ├─ assets/img_001.png …
   └─ manifest.json
```

- **slug 规则**：标题去 `\/:*?"<>|` 等非法字符 → 全角转半角 → 截断 60 字符（中文按 2 计宽）→ 追加 `_YYYYMMDD_<url短哈希6位>`；同目录重名自动 `-2`
- **幂等**：按**文章身份**（`host + /s/xxxx`，写进 manifest 的 `identity`）判断；已有完整产物 → `skipped`，`--force` 强制重跑
  > ⚠️ 不要用整页 HTML 的 `sha256` 当幂等键：公众号页面每次请求都带随机 nonce，整页哈希必然不同（M1 实测踩过这个坑）
- **断点**：每阶段完成即落盘中间产物（`raw.html`、`article.json`），中断后从最近阶段续跑
- **并发**：默认**串行**（渲染是 CPU 密集且要保证顺序）；`--jobs N` 只作用于抓取/图片下载阶段

`manifest.json`：

```jsonc
{
  "schema": "w2d.manifest/1",
  "tool_version": "0.1.0",
  "source_url": "…", "html_sha256": "…", "article_hash": "…",
  "outputs": [{ "file": "article.docx", "format": "docx",
                "sha256": "…", "bytes": 1284312, "renderer": "python-docx-1.2.0" }],
  "assets": [{ "file": "assets/img_001.png", "bytes": 82311, "status": "ok" }],
```

## 10. 关键工程约束

| 约束 | 做法 |
|---|---|
| 代理分流 | 抓微信**必须直连**（`NO_PROXY=mp.weixin.qq.com,mmbiz.qpic.cn`）；装依赖才走 `127.0.0.1:7890`。两个变量分开配，`.env.example` 里写清 |
| 安全 | URL 白名单 `^https://mp\.weixin\.qq\.com/(s\|mp/appmsgalbum)`；HTML 一律视为不可信：删 `script`/`on*`/`javascript:`/`<iframe>` |
| 解析抗改版 | **所有微信选择器只在 `extract/selectors.py` 一处**，配 `samples/` 真实快照做回归测试 |

| 合规 | 产物目录写 `notice`；不实现任何"批量分发/公开分享"能力 |

## 11. 技术选型清单与理由

| 需求 | 选型 | 为什么不选别的 |
|---|---|---|
| 运行时 | **Python 3.12，用已装的 `uv` 拉起** | 本机无 Node；`uv` 已装且能在无管理员权限下建 venv |
| HTTP | `httpx` | 支持 HTTP/2、超时/重试细粒度；比 requests 现代 |
| HTML 解析 | `lxml` + `cssselect` | 公众号 DOM 层级深，XPath/lxml 比 bs4 快一个量级；且 velyvo 已验证可行 |
| Word 生成 | **`python-docx`** | 唯一渲染链；pandoc 丢内联样式、html-to-docx 需 Node 且丢外链图、Word COM 在本机实测崩溃 |
| PDF | 本机 Chrome `--print-to-pdf` | 无需 Playwright/Puppeteer（无 Node），零额外下载 |
| 图片 | `Pillow` | 转码/压缩/取尺寸一把抓 |
| CLI | `typer` + `rich` | 自动 `--help`、进度条好看 |
| Web | `FastAPI` + `Jinja2` + 原生 JS | **刻意不引构建链**（无 Node），单页足够 |
| 配置 | `pydantic-settings` | 与模型同一套校验 |
| 测试 | `pytest` + 真实 HTML fixtures | 改版是必然事件，回归测试是唯一防线 |

## 15. 一页纸总结

```
做什么：粘贴一个公众号文章链接 → 本地生成一个「打开就是原文样子」的 Word
怎么做：URL/页面DOM/粘贴HTML 三通道抓取 → 归一化成 blocks[] → 
        python-docx 渲染成 docx（图片内嵌、样式逐项还原）
靠什么赢：所有开源项目都把 Word 当顺带格式，没人认真做「文字+图片排版」的还原；
         我们用 python-docx 精确控制 run 级样式与图片内嵌，不依赖 Office。
不做什么：不碰已被关闭的后台接口，不做全号历史下载，不绕过任何访问控制。
风险在哪：微信改版（用 selectors 单点 + 样本回归扛）、
         图片防盗链（本地化 + Referer 策略 + 重试扛）。
第一步：M0 探针，先验证"装得上、抓得到、Word 转得动"三件事。
```
